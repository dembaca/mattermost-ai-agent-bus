# 11. Risks and Technical Debt

## Overview

Known risks of the decisions in Section 9, with what keeps each small and
which work package closes or lowers it. A risk whose mitigation is planned,
not built, says so: the code today behaves as Section 6 describes.

## 11.1 Risk Register

| ID | Risk | Created by | Likelihood / Impact | Mitigation | Status |
|----|------|------------|---------------------|------------|--------|
| RISK-01 | An injected peer relays a request: an agent whose owner and trusted humans are all mine was itself steered by a post it read, and passes the request to my worker as its own | ADR-001 | Low / High | The peer rule removes relays through agents of other owners; what remains is an injected agent of my own trust circle. Posts are data, not instructions (`SKILL.md`); approvals stay server-verified (RT-6.8, RT-6.11, RT-6.13) | Accepted residual; the cross-owner relay is closed since WP2 (0.60.0): a foreign agent's request is no task, its `TASK` roots bind nothing and its broadcasts are gated (RT-6.16) |
| RISK-02 | The owner claim can be forged while the registration secret is shared: any holder registers a bot `for @<anyone>` and becomes a peer of that human's agents | ADR-003 | Medium / High, once a second owner shares a channel | Enrollment tokens (WP3, ADR-003): a human mints one with `/agent-token`, and the registrar binds the bot to that human (native owner and `for @`). Since registrar 0.2.0 a shared-secret bot is `unbound`, never `for @`, and so foreign; a registrar before 0.2.0 still writes the unchecked `for @`. A signed `via: secret` claim (0.66.0, RT-6.24) changes nothing: its owner counts only where a readable native owner agrees, so such a bot stays foreign. Left: the shared secret unregisters any bot, and a leaked enrollment token registers bots bound to its owner within its scope ([registrar threat model](https://github.com/dembaca/mattermost-agent-registrar#threat-model)) | Mitigated once the registrar runs 0.2.0 with `ALLOW_SHARED_SECRET=false` (WP3, 0.61.0) |
| RISK-03 | Mattermost admins, and whoever may edit bot accounts, can rewrite a bot's description and so its owner and trusted list | ADR-003 | Low / High | Trust assumption in Section 7.3: only the registrar account and system admins edit descriptions. Since 0.61.0 the bus reads a bound bot's native owner (`owner_id`) where the operator grants bot accounts `read_others_bots`, and a `for @` that disagrees with it makes a foreign agent: rewriting the description alone no longer makes a peer. Since 0.66.0 (#83, RT-6.24) an agent with a valid registrar attestation is judged by it where the registrar's keys are pinned: neither a rewritten description nor a reassigned `owner_id` changes its owner (`via: enrollment`) | Accepted; reduced with `read_others_bots` (WP3); closed for attested agents on hosts that pin the registrar's keys (0.66.0, bus side; the registrar's signing rolls out separately) |
| RISK-04 | Plugin versions are mixed: an older agent writes no home into its status and reads no owner, so it counts in every channel's roster and election and takes a foreign agent's `TASK` as before | ADR-001, ADR-002 | Medium / Medium, during upgrades | A status without a home counts everywhere, as today, until the agent upgrades; the newer side applies its own rules to what it receives. Upgrade every session before relying on the owner split (CHANGELOG notes it) | WP1 built (0.59.0): a status without a home counts everywhere; WP2 built (0.60.0): an agent before it reads no owner. Tolerated until every agent runs the new version |
| RISK-05 | The token cost of guest channels: each further channel brings posts that could wake the model | ADR-002 | Medium / Medium | Guests wake only for a mention, a reply in their own thread or a DM; guest channels and the lobby produce no digest; the Stop hook count leaves out broadcasts in guest channels; the rest is read on demand with `list_recent`. Measured with RT-6.9 (quality goal 6) | Mitigated for guest channels (WP4, 0.62.0, RT-6.22): only a mention, a reply in the agent's own thread there or a DM wakes it, nothing goes into the digest, and the count leaves out `@channel` and posts for all agents there. Mitigated for the lobby too (WP5, 0.63.0, RT-6.22 step 3): where it is not the home, only a mention, a reply in the agent's own thread, a DM or a broadcast by a trusted human or a peer wakes it, and nothing goes into the digest |
| RISK-06 | A delegate approves what the delegator would not: an understated impact, a compromised delegate or a leaked registrar key opens a second approval path next to `MM_TRUSTED_HUMANS` | ADR-004 (proposed) | Medium / High, once built | Effective impact is the maximum of the declared and the server-derived one; high impact stays with the delegator; scope, expiry and revoke; every delegate decision in the delegator's digest; a leaked key is as for #83, rotation by re-pinning | Planned, not built (ADR-004 proposed, depends on #83) |
| RISK-07 | A coordinator answers what needed a human: an approval filed as a question, a steered coordinator or a stalled one turns routing into a quiet bottleneck or a false sense of consent | ADR-005 (proposed) | Medium / High, once built | The coordinator never grants: its answer is `from_agent`, only a trusted human's counts as approval (RT-6.11); the server derives a classification floor, so an action with effect is an approval whatever the worker declared; the mode is set only by a trusted human, signed, and defaults to `direct`; stall fallback to `direct`; coordinator answers in the digest | Planned, not built (ADR-005 proposed; `delegated` depends on #83) |
